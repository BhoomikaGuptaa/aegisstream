# AegisStream Research Methodology

## Research Question

**Can live prompt-response streams be used as online behavioral evidence for measuring LLM reliability, safety, and deployment readiness?**

## Problem Statement

Offline LLM benchmarks (MMLU, HumanEval, MT-Bench) measure capability under controlled conditions. However, deployed LLMs encounter:

- Dynamic and adversarial prompt distributions
- Retrieval-augmented pipelines with variable context quality
- Latency and cost constraints that shift under load
- Evolving user behavior and prompt injection attacks
- Model drift as fine-tuning or provider updates occur silently

AegisStream studies whether streaming telemetry — prompt, response, latency, cost, and metadata — can provide useful, lightweight, interpretable signals for online reliability evaluation.

## Sub-Questions

1. Can lightweight pattern-matching and heuristic evaluators identify outputs requiring human review with acceptable precision?
2. Which failure modes (injection, hallucination, over-refusal, etc.) are easiest and hardest to detect from prompt-response telemetry alone?
3. How do open-source models compare in reliability, safety, refusal quality, latency, and cost under simulated deployment traffic?
4. Can streaming rolling-window statistics detect rising adversarial traffic or hallucination rate drift in time to trigger an alert?
5. Can deployment readiness gates reduce risky releases without excessive false positives?

## Methodology

### Synthetic Benchmark Design
Events are generated by `SyntheticGenerator` with configurable per-scenario injection rates. Scenarios include:

| Scenario | Description |
|---|---|
| normal | Clean, factually correct responses |
| hallucination | Known factual errors injected |
| injection | Prompt injection patterns in user input |
| jailbreak | Jailbreak framing in prompt |
| jailbreak_compliance | Model appears to comply with jailbreak |
| sensitive_data | PII in prompt or response |
| over_refusal | Model refuses safe request |
| rag_grounded | RAG response uses retrieved context |
| rag_ungrounded | RAG response ignores retrieved context |
| malformed | Invalid JSON when JSON expected |
| high_latency | Simulated slow inference |
| high_cost | Simulated large token request |
| drift | Rates increase post-threshold (simulates model shift) |

### Evaluator Design Philosophy
Evaluators are **stateless, lightweight, and interpretable**. They use:
- Regular expressions for PII/card detection
- Keyword pattern matching for injection/jailbreak signals
- Token overlap heuristics for groundedness and hallucination
- Threshold comparisons for SLA and cost metrics
- Rolling window statistics for drift

This design prioritizes:
- **Speed**: <1ms per evaluator, enabling 1000+ events/min throughput
- **Explainability**: each result includes `label`, `explanation`, and `evidence`
- **No external dependencies**: no LLM calls required for evaluation

### Measurement
For each experiment, we report:
- `avg_risk_score` and `avg_reliability_score`
- `review_rate_pct`: fraction of events flagged for human review
- `blocking_rate_pct`: fraction triggering deployment gate failure
- `top_failure_modes`: most common labels from failing evaluators
- `throughput_eps`: events evaluated per second
- Per-evaluator latency (µs)
